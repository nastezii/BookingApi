# Booking API — Лабораторна робота №1

REST API для системи бронювання з JWT-автентифікацією.

---

# Мета роботи

Створити базовий CRUD API для системи бронювання без використання складної архітектури та патернів.

---

# Технології

- ASP.NET Core Web API
- Entity Framework Core
- SQLite
- JWT Authentication
- Swagger
- xUnit

---

# Реалізовано

- CRUD для бронювань
- Реєстрація користувачів
- Авторизація користувачів
- JWT-автентифікація
- Захищені ендпоінти
- Swagger документація
- Unit та integration тести
- Валідація бізнес-правил

---

# Домен

Система бронювання часових слотів.

Користувачі можуть:
- реєструватися
- логінитися
- створювати бронювання
- переглядати бронювання
- редагувати бронювання
- видаляти бронювання

---

# Use Cases

## Реєстрація користувача

### Актор
Користувач

### Передумови
- email ще не існує

### Основний сценарій
1. Користувач вводить email і пароль
2. Система створює нового користувача
3. Дані зберігаються у базі

### Альтернативні сценарії
- невалідний email
- email вже існує

---

## Логін користувача

### Актор
Користувач

### Передумови
- користувач зареєстрований

### Основний сценарій
1. Користувач вводить email і пароль
2. Система перевіряє дані
3. Генерується JWT token

### Альтернативні сценарії
- неправильний email
- неправильний пароль

---

## Створення бронювання

### Актор
Авторизований користувач

### Передумови
- користувач авторизований
- часовий слот валідний

### Основний сценарій
1. Користувач надсилає дані бронювання
2. Система перевіряє правила
3. Бронювання зберігається

### Альтернативні сценарії
- час у минулому
- некоректний діапазон часу
- конфлікт бронювань

---

# Бізнес-правила

- email повинен бути валідним
- email має бути унікальним
- час початку не може бути в минулому
- час завершення має бути після початку
- бронювання не можуть конфліктувати між собою

# Архітектурні особливості

У лабораторній роботі №1:
- бізнес-логіка знаходиться у контролерах
- ORM-моделі використовуються напряму
- контролери працюють безпосередньо з DbContext
- відсутній окремий domain layer

---

# Недоліки архітектури

- сильна залежність від Entity Framework
- складніше тестування бізнес-логіки
- контролери перевантажені логікою
- складніше масштабування проєкту
- складніше змінювати базу даних
